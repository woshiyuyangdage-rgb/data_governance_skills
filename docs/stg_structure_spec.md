# STG Structure Suggestion Specification

## 1. Skill Positioning

`stg_structure_suggestion` is a structure recommendation skill for one source table at a time.

Its goal is not to generate executable DDL or SQL. Its goal is to produce:

1. a recommended STG table name
2. a recommended STG field structure
3. a source-to-target field suggestion list
4. explicit notes and manual review points

## 2. Input Dependencies

The skill uses these inputs:

1. source table metadata parsed from CSV or Excel
2. naming enhancement results
3. standard mapping recommendation results
4. lightweight STG rules and field transform rules

The current version is fully local and rule-based.

## 3. Output Structure

The current output contains:

1. `stg_table_suggestions`
   - one source table to one STG table suggestion
2. `field_suggestions_flat`
   - flattened field suggestion rows for UI and report export
3. `issues`
   - low-confidence or technical-reservation review points
4. `summary`
   - concise run summary

Each field suggestion includes:

- source field name and type
- recommended STG field name
- recommended data type
- mapping source
- action
- notes

## 4. Field Suggestion Logic

Current priority order:

1. standard mapping first
2. naming enhancement second
3. original source field fallback last

Detailed rules:

1. If a field already maps to a standard field:
   - use the standard field name first
   - use the standard Chinese name first when available
2. If a field is not mapped but naming enhancement has a stronger suggestion:
   - use the naming suggestion
3. Otherwise:
   - keep the original field with minimal normalization

Data types are normalized through `field_transform_rules.yaml`.

STG table names are generated by:

1. removing configured source prefixes
2. normalizing the remaining table name
3. adding the configured `stg_` prefix

## 5. Manual Confirmation Points

The current version intentionally surfaces manual review needs:

1. low-confidence mapped fields
2. technical or audit reservation fields
3. fields with fallback naming
4. tables that still contain review flags after suggestion generation

These are intended for human confirmation before any downstream physical modeling work.

## 6. Current Boundary

Current boundaries are explicit:

- no executable DDL generation
- no executable SQL generation
- no complex split or merge rules
- no cross-table consolidation
- no semantic inference or AI planning
